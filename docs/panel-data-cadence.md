# Panel 分层刷新与采集周期

2026-11-03 确认的执行顺序：先补齐规范，再修改代码与迁移后的运行配置，最后验证真实线上界面。修改前的 76 个 Panel 清单保留在 [周期与 WorldMonitor 架构核验记录](../document/开发/Panel数据更新周期与WorldMonitor架构核验记录-2026-11-03.md)，不覆盖历史证据。

## 统一原则

浏览器检查、后台采集尝试、来源观察／发布时间、缓存保留期限是四个不同的时钟。定时返回一次响应不代表来源更新；重复缓存不能改写报价、K 线或发布时间。来源失败继续保留错误语义，合法的空结果可以替换旧列表。共享数据由同一数据拥有者采集，前端通过公共 Runtime 合并需求。

参考 WorldMonitor 按来源节奏安排工作的思想：概览通常按分钟检查，发布型统计按小时检查。具体版本和源码证据见上述核验记录。它的市场概览周期不能直接用于我们的选中盘口、订单流及合约指定源。

公共 Runtime 未显式声明时采用 `fast=60 秒`、`slow=10 分钟`；`bootstrap/manual` 默认不定时轮询。领域资源显式周期优先。隐藏页面、无可见消费者时暂停需求；手动刷新仍立即可用。保留请求取消、截止时间、Retry-After、有限快速重试和后续退避。

商品与加密概览的快照时效改为 15 分钟，保留上限仍为原始时钟起算的 15 分钟；Funding 时效为 3 分钟、保留上限 15 分钟。这样正常采集间隔不会被判为过期而触发补抓。报价本身的有效性和来源错误继续由领域规则判定，不通过刷新时钟掩盖错误。

混合加密资源有可见策略消费者时仍每 30 秒读取，但 worker 内部对慢来源独立计时。成功缓存保留原观察时间，失败也等待该来源的下一次尝试窗口。重启后首次采集会重新建立进程内缓存；这不是跨重启持久化的配额管理。

## 修改边界

- 前端：公共 Runtime、现有资源声明、共享工厂和健康摘要检查；不改布局、字体或 Panel 的启用规则。
- 后端：既有加密策略 worker 的来源调用周期，概览／Funding／DeFi／Radar／新市场信号的配置，以及与周期匹配的时效。
- 运行环境：只修改迁移后的相关本机服务；沿用现有网络和代理配置，已停用的 GCP 采集与专用转发保持停止。
- 测试：验证实际调度请求数、手动与隐藏行为、共享消费者、来源时间保留、失败节流、慢来源缓存与未完成 K 线。

## 验收方法

1. 执行相关单元、浏览器、构建和仓库要求的检查；原有失败单列。
2. 只提交本次文件／改动块，推送 main，用 `git archive` 导出确切提交构建前端。
3. 发布前确认迁移后的实际目的地；不得因为旧部署脚本仍写 GCP 就恢复旧服务。
4. 保存已安装文件哈希、运行进程参数、采集日志、快照时间。区分尝试发生与来源数据真正更新。
5. 在真实公网 URL 上验证桌面和手机截图、发布版本、实际请求；不替换 API 或瓦片。明确请求计数的观察时长。
6. 30 分钟、6 小时等长周期通过配置与调度测试佐证；短时观察不能声称已覆盖整个周期。

## 未纳入本次完成结论的事项

来源访问失败、SOL／XRP 指定源接入、历史流入实时化、Trade Policy 动态化，以及发布日历驱动调度需分别验收。降频不能把失败变成成功，不能把静态／历史内容写成实时更新。停用生产者不会在本次擅自启动。
