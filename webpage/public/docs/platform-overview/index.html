Platform & Features

Platform Overview

polyData Monitor is a Polymarket intelligence platform built around one idea: a market should be inspected as a living system, not as a single price chart. The platform joins market identity, order-book state, chain-level fills, oracle resolution, external context, and AI summaries into a single operational surface.

The product is designed for researchers, traders, builders, and operators who need to answer three questions quickly: what is the market, what is happening inside it, and what could change its resolution or liquidity profile.

Platform shape

The workspace combines Python collectors, PostgreSQL market and oracle serving tables, ClickHouse high-volume trade storage, Redis runtime cache, SQLite snapshot fallback, a Flask API, and a Vite/Preact dashboard. Each layer is allowed to fail independently so the interface can show cached, stale, empty, or degraded states instead of silently hiding missing data.

Layer Purpose Primary assets
Data collection Discovers markets, hydrates token identity, scans chain events, and refreshes external feeds. Gamma, CLOB, Polygon RPC, UMA oracle logs, RSS/news, finance, weather, sports, crypto feeds.
Storage Separates canonical market metadata from high-volume fill history and runtime snapshots. PostgreSQL, ClickHouse, Redis, SQLite fallback snapshots.
Serving API Normalizes backend state into dashboard-ready endpoints with clear status and cache metadata. Flask services under /wm-api/, panel registry routes, market workspace APIs.
Interface Presents markets through panels, map/context surfaces, lifecycle state, search, and operator workflows. Vite/Preact frontend, docs pages, public static deployment.

Data plane

The data plane starts with market identity. polyData collects Gamma events and markets, resolves CLOB slugs and token ids, and supplements missed markets from on-chain exchange registry events. This gives each market a stable identity made from question text, slug, condition id, outcome tokens, event context, and series context when available.

The chain index then adds execution and resolution truth. OrderFilled rows capture maker/taker fill activity, token flow, price, size, and fees. Oracle rows capture request, proposal, dispute, settlement, transaction hashes, block numbers, proposed prices, settled prices, and matching metadata.

Runtime plane

The runtime plane is optimized for repeated dashboard reads. Expensive sync and enrichment work runs outside the browser. The frontend reads normalized endpoints through /wm-api/, which lets Nginx route browser requests to the active API service without exposing private hosts or deployment details.

Runtime responses should carry enough status for the UI to be honest: fresh when a watcher is current, cached when a recent snapshot is still usable, stale when the system is behind, empty when no data exists, and degraded when an upstream source or local worker is unavailable.

Analysis plane

The analysis plane connects market movement to causes and risks. It combines price history, best bid/ask, order-book depth, OrderFilled flow, oracle status, external content, macro context, and generated summaries. The goal is not to replace analyst judgment; it is to compress the first pass so an analyst can decide what deserves deeper review.

Signal family What it explains Typical panels
Market state Whether a market is discoverable, tradeable, active, closing, in oracle review, settled, or archived. Market workspace, lifecycle view, active market scanners.
Trading flow Where liquidity, volume, maker/taker activity, and unusual fill patterns are forming. OrderFilled analytics, signal intelligence, liquidity panels.
Resolution risk Whether oracle state, proposal status, disputes, or settlement timing could affect final outcome. Oracle watch, settlement monitor, matched UMA event panels.
External context Which news, macro, sports, weather, finance, or crypto catalysts may explain a move. News panels, macro panels, finance and crypto context panels.

Panel surface

The dashboard currently registers 68 panels. Panels are small modules with explicit metadata, fetch behavior, rendering logic, and degraded-state handling. This makes the interface extensible: a new data source can be added as a panel without rewriting the whole market workspace.

Panel groups cover market discovery, market workspace context, chain flow, oracle resolution, AI summaries, finance context, crypto context, macro context, weather, sports, and time-aware tools. The panel system is intentionally modular because Polymarket questions cross many domains.

Operator workflows

polyData is built around workflows rather than isolated charts. A typical workflow starts from market discovery, opens a market workspace, checks price and liquidity, inspects OrderFilled activity, verifies oracle state, reviews external catalysts, then saves or shares the resulting context.

For live monitoring, the priority is fast triage: identify markets with active movement, verify whether the movement is real liquidity or thin-book noise, check whether resolution risk is nearby, and decide whether the market needs manual review.

Reliability model

The platform assumes upstream data can be partial, delayed, or inconsistent. Gamma and CLOB are useful but not complete historical truth; Polygon logs are authoritative but require identity matching; oracle events are precise but sometimes need adapter and ancillary-data decoding. The serving layer therefore records provenance, cache status, and matching confidence where possible.

This reliability model is visible in the product: panels should show what source they used, whether data is fresh or cached, and what part of the lifecycle is currently known. The result is a system that can be used during live market movement without pretending every upstream dependency is perfect.
